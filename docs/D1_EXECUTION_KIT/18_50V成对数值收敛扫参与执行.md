# 第18章：解决50V严格配对停算的成对数值收敛扫参

目标：原有**同模型配对控制**虽在故障前完全配对（0mV偏差），但A/B分别停算250.151/254.980µs，无法和各自的完整320µs候选比较。禁止使用另一套`Vt=10`门极开关控制（故障前Vout差13–18mV）来凑齐两个条件。

本包在完全相同的既有四组电路上，只改变LTspice `.options cshunt`，按成对同参数方式生成 12份诊断deck：2fF、5fF、10fF，每一种都包含 `A_CONTROL/A_CANDIDATE/B_CONTROL/B_CANDIDATE`。**这是数值敏感性研究，不是添加实际并联电容、不是硬件保护方案，也不表明已收敛。**

## 本次新增的实际可执行文件

- 12份 `.cir` 已存储于 `sim/v3/d1_prot03_shunt_{2f,5f,10f}_{A_CONTROL,A_CANDIDATE,B_CONTROL,B_CANDIDATE}.cir`；每份含源模型和完整320µs窗口，只有 `.options cshunt` 与两行标识注释发生变动。
- 受控 [12例执行清单](../../design/v3/power_priority/prot03_solver_sweep_plan.json) 的 `simulation_state` 全为 UNRUN、`not_for_fab=true`，不能把“生成”写成“仿真完成”。
- `python tools/generate_prot03_solver_sweep.py --check` 逐文件与原deck比较；`python -m pytest tools/test_generate_prot03_solver_sweep.py -q` 拦截任何非cshunt电路改变。

## Windows执行

先做最小2fF组，以便检查是不是数值卡死所致：

```powershell
pwsh -File tools/run_d1_50v_matched_cases.ps1 -Variant shunt_2f
pwsh -File tools/run_d1_50v_matched_cases.ps1 -Variant shunt_2f -Cases B_CONTROL,B_CANDIDATE -Execute -RunId solver_2f_B_001 -LTspice 'C:\Program Files\ADI\LTspice\LTspice.exe'
```

若在2fF下仍无法得到完整对照，再同样使用`shunt_5f`和`shunt_10f`。**每种cshunt都必须控制+候选成对运行**，不允许用1fF候选与5fF对照混合。脚本继承之前的不可覆盖/RAW/LOG/哈希记录。输出文件保存失败前缀和完整运行状态后，再用 `protection_candidate_compare.py` 成对重算新JSON，不覆盖历史发布的PROT-03报告。

本机执行策略禁止运行 `.ps1`（`powershell -File` 直接 `UnauthorizedAccess`），因此同一契约由 Python 移植版执行，`-Variant` 对应 `--variant`：

```bash
python tools/run_d1_50v_matched_cases.py --variant shunt_2f            # dry-run，只列 deck
python tools/run_d1_50v_matched_cases.py --variant shunt_2f --execute \
    --run-id solver_2f_B_001 --cases B_CONTROL B_CANDIDATE \
    --ltspice D:/ADI/LTspice/LTspice.exe
```

移植版的 cshunt 门槛按变体取值（`published`=1e-15、`shunt_2f`=2e-15、`shunt_5f`=5e-15、`shunt_10f`=1e-14），所以“1 fF 候选配 5 fF 对照”会被直接拒绝；`run_manifest.json` 还额外记录 `variant` 与 `required_cshunt_farads`，扫描归档不会被误当成已发布的 1 fF 证据。

## 可接受判据和失效条件

1. 每组控制与候选双方最后保存时间均达到320µs，原始日志包含`Total elapsed time`，不仅是求解器处理了部分波形。
2. 140–175µs故障前Vout均值差≤1mV；在同一控制类、相同器件与开关模型下对比。
3. 2fF、5fF、10fF对峰值、起动瞬态与故障后8SR门极的影响必须另列；若cshunt变化导致主电路工作点或门极末态显著改变，就只能归为**数值敏感性**，不是“保护有了确定收益”。
4. 完整判断需要真实比较器、UCC27282 EN及NCP4306/UCC27524A的门级关断延时模型。旧PROT-B `0.05Ω`理想钳位与新物理实现不同。第三象限SOA/磁件L(I)依旧阻塞。

## 2 fF 组：配对控制第一次跑满 320 µs

`--variant shunt_2f` 的 **A_CONTROL**（run `solver_2f_A_001`）跑满 **320.000 µs**（457.205 s，1.17 GB）。这是 50 V 的 thrmute 配对控制第一次走完整个保存窗口——1 fF 下它每次都停在 250.151 µs。

**只加 2 fF 没有把物理改掉**（`hotfault_convergence.py`，两侧都取 0–220 µs 冻结窗口，`circuit_differences()` 为 0 条，`checks` 全绿；记录 `solver_sweep_2f_A_CONTROL_convergence.json`）：

| 量 | 1 fF 控制 | 2 fF 控制 | 相对 |
|---|---|---|---|
| trip | 215.1704 µs | 215.0232 µs | −147 ns（−0.068 %） |
| `I(Lr)` 峰 | 100.988 A | 101.069 A | +0.080 % |
| SR 正向峰 | 304.960 A | 303.411 A | −0.508 % |
| SR 反向峰 | 13.339 A | 13.759 A | +3.15 % |
| `V(oc)` 最大 | 1.0871 V | 1.0901 V | +0.28 % |
| 故障后 `V(out)` 最低 | 0.9341 V | 0.9449 V | +1.15 % |

三个头部峰值移动都在 1 % 内；唯一大幅移动的是 SR 反向峰（+3.15 %），它与最初引入 1 fF 时移动 −1.67 % 属于同一类“接近零、斜率大”的量，因此按数值敏感性引用，不能当电路变化。采样步数从 986 420 降到 432 537（同一 220 µs 窗口，2.28 倍），说明省下的是求解步而不是求解精度之外的物理。

**窗口必须写 220 µs，不能写成 250 µs**：同一条比较若把窗口放到 250 µs，两侧 raw 在 249.997 / 249.998 µs 之后就没有采样点，`the_comparison_window_is_covered_by_both_raws` 会（正确地）报 false；`vout_min_after_engage_v` 的符号也会随窗口翻转（250 µs 窗口是 −1.14 %）。220 µs 是既有 SOLVER_DIAGNOSTIC 的冻结窗口，也是这里记录的那个。

候选侧（run `solver_2f_A_002`）随后也跑满 **320.000 µs**（440.638 s、1.11 GB）。用同一 2 fF 的两条 raw 成对复算（必须显式传 `--base-deck`/`--candidate-deck`，不能用 1 fF 的默认父 deck——`mixed_sweep_variants()` 现在把这条写成硬错误，混用两种 cshunt 会在读 raw 之前就被 CLI 拒绝）写出 `protection_candidate_50v_120a_prot_a_paired_shunt_2f.json`，**七项 `checks` 全为 true**，包括一直为 false 的 `the_declared_window_is_fully_covered`：

| 量 | 2 fF 控制 | 2 fF 候选 |
|---|---|---|
| 尾部保存时间 | 320.000 µs | 320.000 µs |
| 故障前 `V(out)` 均值（140–175 µs） | 1.943736647 V | 1.943736647 V（差 **0.000000 mV**） |
| trip | 215.0232 µs | 215.0232 µs |
| 锁存 | 215.0925 µs（延时 69.3 ns） | 215.0925 µs |
| SR 正向峰 | 303.411 A | 303.411 A |
| SR 正向 I²t 合计 | 4.753844 A²s | 4.721685 A²s（**−0.676 %**） |
| 故障后 `V(out)` 最低 | 0.7444 mV | 0.7328 mV（差 −0.0116 mV） |
| 八只 SR 门极末端为高 | 0 只 | 0 只 |

这是 50 V 第一次**同时**满足“两侧跑满 320 µs”和“故障前 ≤1 mV”两条判据——1 fF 下它们互斥。三处必须照原文读，不能外推：

- 峰值两侧逐位相同，因为两 deck 在触发前逐位相同（1 fF 配对也是这样），不是“保护没有作用”；候选的收益体现在 I²t（−0.676 %）与门极关断时序上。
- 控制端门极在 trip 后**回到高电平直到 237.459 µs**才落下，末端为高的只数（1 fF 3 只、2 fF 0 只）是**求解器选的末态**，不是“2 fF 更安全”。`all_candidate_gates_low_at_end` 只说明候选侧这一刻的记录，`hardware_continuous_rating_approved` 与 `safety_proof` 都仍是 **false**。
- `cshunt=2e-15` 是求解器正则化，不是电路里加了电容；本组只说明**此数值设置下的成对可比性**，`fabrication_approved` 仍为 false。

## B 组：2 fF 让控制侧走得更远，但直接失败

同一 `--variant shunt_2f` 的 **B_CANDIDATE**（run `solver_2f_B_001`）跑满 320.000 µs；**B_CONTROL 没有跑完**，而且不是被超时终止：

```
Convergence Failure:  Time step too small; time = 0.00226451, timestep = 1.25e-18:
                      trouble with instance "xsr3:x2:Bage"
Simulation Failed: Iteration limit reached
Total elapsed time: 1374.729 seconds.
```

- 1 fF 的 B 控制在 1800 s 超时被杀时停在 **254.980494 µs**；

**2 fF 没有改物理**（`hotfault_convergence.py`，两条控制 deck 只差 `.options`，`circuit_differences()` 为 0 条，220 µs 冻结窗口覆盖两条 raw，`checks` 全绿；记录 `solver_sweep_2f_B_CONTROL_convergence.json`）：

| SR 正向峰 | 303.559 A | 304.223 A | +0.219 % |

所以 B 组在 2 fF 上**不成立**：没有成对结论可写，`B_CANDIDATE` 的单边 320 µs 不能与 1 fF 控制配对，也不能与 2 fF 控制配对（它没跑完）。按本包的成对规则，只能整组换参数重跑。

## 5 fF 组：控制侧反而更早停，两条判据仍不能同时成立

`--variant shunt_5f` 的 **B_CANDIDATE**（run `solver_5f_B_001`）跑满 **320.000 µs**（1435.723 s、2.14 GB）；**B_CONTROL 又在 1800 s 预算上被杀**，停在 **235.889681 µs**（6.87 GB，日志里 **75 次** `tolerance relaxed`，没有 `Total elapsed time`，也没有 `Simulation Failed`）。

| cshunt | B 控制停在哪 | 退出方式 | raw |
|---|---|---|---|
| 1 fF | 254.980 µs | 1800 s 超时被杀 | 4.59 GB |
| 2 fF | 264.515 µs | 求解器自己放弃（`timestep = 1.25e-18`） | 2.75 GB |
| **5 fF** | **235.890 µs** | **1800 s 超时被杀** | **6.87 GB** |

**阶梯不单调**：2 fF 走得比 1 fF 远 9.5 µs，5 fF 反而比 1 fF 少 19.1 µs。三条 raw 的尾部采样步长都落在亚飞秒（1 fF 0.02–0.08 fs、5 fF 0.08–0.32 fs；2 fF 在 38 fs→0.019 fs 的最后几个采样之后由求解器报失败）——**cshunt 没有消除那次塌缩，只改变了它发生在哪一刻、以什么方式退出**。所以"再加一点 cshunt 就更好"没有任何先验依据，这一组也不是整组换参数重跑的候选。

**配对判据在 5 fF 上照样成立**（`protection_candidate_50v_120a_prot_b_paired_shunt_5f.json`，用 5 fF 控制与 5 fF 候选成对复算）：故障前 140–175 µs 的 `V(out)` 均值差 **0.000000 mV**，`the_pre_fault_operating_points_match_within_1_mv` 为 **true**；失败的是另一条——`the_declared_window_is_fully_covered` 为 **false**，因为控制停在 235.890 µs。也就是说 **≤1 mV 那条从来不是瓶颈**，1/2/5 fF 三档都满足；卡住的始终是"两侧跑满 320 µs"。

**5 fF 没有改物理**（`hotfault_convergence.py`，两侧 0–220 µs 冻结窗口，`circuit_differences()` 0 条，`checks` 全绿；记录 `solver_sweep_5f_B_CONTROL_convergence.json` / `solver_sweep_5f_B_CANDIDATE_convergence.json`）：

| 量 | 1 fF 控制 | 5 fF 控制 | 相对 |
|---|---|---|---|
| trip | 215.0024 µs | 215.0578 µs | +0.0258 % |
| `I(Lr)` 峰 | 101.011 A | 100.866 A | −0.1428 % |
| SR 正向峰 | 303.559 A | 303.451 A | −0.0354 % |
| SR 反向峰 | 13.367 A | 13.646 A | +2.09 % |
| `V(oc)` 最大 | 1.08944 V | 1.08859 V | −0.0786 % |
| 故障后 `V(out)` 最低 | 0.93974 V | 0.93990 V | +0.0172 % |

| 量 | 1 fF 候选 | 5 fF 候选 | 相对 |
|---|---|---|---|
| `I(Lr)` 峰 | 45.787 A | 46.442 A | +0.0143 % |
| SR 正向峰 | 138.455 A | 139.371 A | +0.0066 % |
| SR 反向峰 | 8.361 A | 7.401 A | −0.115 % |
| `V(oc)` 最大 | 0.70688 V | 0.70631 V | −0.081 % |
| 故障后 `V(out)` 最低 | 0.091368 V | 0.091376 V | +0.0098 % |

三个头部峰值移动都 ≤0.15 %；唯一越过 1 % 的仍是 SR 反向峰（+2.09 %），与 1 fF 引入时移动 −1.67 % 属同一类"接近零、斜率大"的量。**候选两侧的 `trip_s` 都是 `null`**：`V(oc)` 峰只有 0.7069 / 0.7063 V，从未越过 UCC25600 Level-1 的 1 V——候选在 **185.278 µs** 被自己 1.8 V 的 `V(ocdf)–V(ocm)` 比较切掉（锁存 185.348 µs，比控制的 215.058 µs 早 **29.78 µs**），原边电流没来得及把 CT 负载推到 1 V。所以那张表的峰值是**整个 0–220 µs 窗口**的，不是"投入→trip"的。

两处不能照字面外推：

- 配对 JSON 的公共切片止于 **235.890 µs**，不是 320 µs。切片上候选的 `vout_min` 是 0.0293 V、控制是 0.2961 V（`relief.vout_min_delta_mv` = −266.8 mV），这**不是**"保护把输出拉低了"：候选真的关断了，控制是被杀在半路的。两个末态不可比，只能当覆盖不足的记录。
- 控制行 `gate_high_after_fault = 4`（1b/2b/3a/4b）是**被杀那一刻**的门极状态，不是故障结束态；配对 JSON 的 `limits` 已经把 `the common slice ends at 235.890 us` 写进去。

**10 fF 没有跑**，理由三条：阶梯已经证明非单调（第二次失败就该换假设，而不是继续加 cshunt）；cshunt 对行为源 `xsr3:x2:Bage` 的跳变没有直接作用，没有机制论证支持"再多一点"；以及本机 D: 只剩 5.5 GB，而 5 fF 的前缀已经写到 6.87 GB。要判收敛得先把工作点钉住（见 `sr_step_operating_point*.json`），不是继续减步长或加正则。

**修了一个会把这类结论判反的缺陷**：`hotfault_convergence.py` 原先要求窗口内最后一个采样点距离窗口终点 ≤1 ps。采样点不可能落在边界上，`window_peaks` 返回的是边界**之前**的最后一个点——5 fF 候选的两条切片止于 219.9966 / 219.9990 µs，两条 raw 都覆盖了整个 220 µs 窗口，检查却报 false。现在容差取 deck 自己的 `.tran` Tmaxstep（这里 5 ns，`max_step_s()`），并写进 `results.coverage_tolerance_s`，读的人能看到放宽了多少。放宽的只有**窗口覆盖**这一项；判断"整条 raw 有没有跑到终点"的 `reached_stop()` 仍是 1 ns，48 V 对照那条既有结论不变（两次都在 320 µs 上落地，差 0 ns 数量级）。

**归档 manifest 的 `tail_us` 是事后补的**：`out/d1_50v/solver_5f_B_001/run_manifest.json` 由修复前的模块在内存里写出（进程按 1800 s 预算被杀时 `TimeoutExpired` 会先于分类抛出，控制行因此记成 `tail_us: null`），现在用同一个工具的 `classify()` 从归档 raw 重新读出 **235.889681**。进程返回码那条路径已在 `2639f2b` 修好，超时路径的回归测试是 `test_a_run_killed_on_the_timeout_keeps_its_prefix`。

## 2026-11-03 追溯修正：2 fF 实验源文件的换行符哈希

本轮检查发现2 fF A组的实验登记SHA-256与Git提交中的 `.cir` 不一致。逐字节核算确认：登记的原散列**恰好等于同一源文本从LF转成Windows CRLF后的散列**，电路文本与`.options cshunt=2e-15`并未变化。为了避免GitHub Actions把不同操作系统的换行符当电路变更，本轮将登记表的 `deck_sha256` 统一为**仓库规范化LF文本的SHA-256**，同时把运行时原始CRLF SHA-256单独保存在 [双哈希证据JSON](../../design/v3/power_priority/prot03_2f_A_deck_hash_provenance.json)；对照源文件逐字节归一化的自动测试证明二者仅换行符不同。**RAW/LOG的历史SHA-256原样保留**，不能把文本规范化推广到波形数据。未重新运行仿真，也未修改电路。
